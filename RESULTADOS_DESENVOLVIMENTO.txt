1. RESUMO DO PROJETO
================================================================================

CorreX é uma API REST completa desenvolvida em Spring Boot 3 com Java 17 para
um sistema de correção automática de redações utilizando inteligência artificial
(GPT-4o-mini da OpenAI).

O sistema permite que professores:
  • Gerenciem turmas e alunos
  • Definam critérios de avaliação com pesos personalizáveis
  • Recebam redações por texto ou upload de arquivo (PDF, DOC, DOCX, TXT)
  • Obtenham correções automáticas com notas por critério
  • Façam revisões manuais das correções
  • Visualizem estatísticas em um dashboard

9. FLUXOS PRINCIPAIS
================================================================================

FLUXO 1: AUTENTICAÇÃO
────────────────────────────────────────────────────────────────────────────
1. Professor faz POST /api/v1/auth/register com (nome, email, senha)
2. AuthService verifica se email existe
3. Criptografa senha com BCrypt
4. Salva Professor
5. Gera JWT com JwtService (válido por 24h)
6. Retorna LoginResponse (token, nome, email)

7. Próximos requests incluem header: "Authorization: Bearer {token}"
8. JwtAuthenticationFilter valida token
9. Popula SecurityContextHolder com usuário autenticado

FLUXO 2: ENVIO E CORREÇÃO DE REDAÇÃO (TEXTO)
────────────────────────────────────────────────────────────────────────────
1. Professor faz POST /api/v1/redacoes/texto com (texto, idioma, turmaId, nomeAluno)
2. RedacaoService valida critérios (soma deve ser 100%)
3. Resolve aluno (novo ou existente)
4. Cria Redacao com status PROCESSANDO
5. Chama OpenAiService.corrigirRedacao()
6. OpenAiService monta prompt instruindo GPT-4o sobre:
   - Texto da redação
   - Critérios + pesos do professor
   - Formato JSON esperado
7. Recebe resposta JSON:
   {
     "notaFinal": 7.5,
     "comentarioGeral": "Boa redação...",
     "notas": [{"nomeCriterio":"Gramática","peso":30,"nota":7.0}],
     "erros": [{"categoria":"Grammar","textoOriginal":"a","textoCorrigido":"an"}]
   }
8. Cria Correcao + NotaCriterio + ErroEncontrado
9. Atualiza status da redação para CORRIGIDA
10. Retorna RedacaoResponse com tudo preenchido

FLUXO 3: ENVIO E CORREÇÃO DE REDAÇÃO (ARQUIVO)
────────────────────────────────────────────────────────────────────────────
1. Professor faz POST /api/v1/redacoes/upload com arquivo (PDF/DOC/DOCX/TXT)
2. FileService.extrairTexto():
   - Detecta extensão
   - Se PDF: usa PDFBox (PDFTextStripper)
   - Se DOCX: usa POI (XWPFDocument)
   - Se DOC: usa POI (HWPFDocument)
   - Se TXT: lê diretamente UTF-8
3. Valida se texto não está vazio
4. Segue fluxo similar ao FLUXO 2 (mesmas correções)
5. Armazena metadados (nome, tipo, tamanho)

FLUXO 4: REVISÃO DE CORREÇÃO
────────────────────────────────────────────────────────────────────────────
1. Professor acessa redação corrigida (GET /api/v1/redacoes/{id})
2. Analisa a correção da IA
3. Faz PUT /api/v1/redacoes/{id}/revisao com:
   - textoEditado (opcional)
   - notaFinalManual (sobrescreve nota da IA)
   - feedbackExtra (comentário do professor)
4. RedacaoService atualiza Correcao e Redacao
5. Status muda de CORRIGIDA para REVISADA
6. Pode fazer PUT /api/v1/redacoes/{id}/enviar
7. Status muda para ENVIADA (pronto para comunicar aluno)

FLUXO 5: DASHBOARD
────────────────────────────────────────────────────────────────────────────
1. Professor faz GET /api/v1/dashboard
2. DashboardService calcula:
   - totalCorrecoes = redações em status CORRIGIDA + REVISADA + ENVIADA
   - alunosAtivos = count distinct alunos
   - mediaGeral = média aritmética de todas as notas finais
   - pendentes = redações em status PENDENTE + PROCESSANDO
   - correcoesRecentes = últimas 5 redações ordenadas por data
3. Retorna DashboardResponse com tudo preenchido
4. Frontend usa dados para exibir cards de resumo

11. FLUXO DE SEGURANÇA
================================================================================

AUTENTICAÇÃO
────────────────────────────────────────────────────────────────────────────
1. Credentials (email + senha) -> POST /api/v1/auth/login
2. AuthService valida contra Professor salvo no BD
3. Compara senha com BCrypt
4. JwtService gera token com algoritmo HS256 (HMAC + SHA256)
5. Token expira em 24 horas
6. Client armazena token em localStorage/sessionStorage

AUTORIZAÇÃO
────────────────────────────────────────────────────────────────────────────
1. Client inclui token no header: "Authorization: Bearer {token}"
2. JwtAuthenticationFilter intercepta request
3. Extrai token do header
4. JwtService valida:
   - Assinatura (segura contra tampering)
   - Expiração
   - Formato
5. Se válido: extrai email do token
6. CustomUserDetailsService carrega Professor do BD
7. Popula SecurityContextHolder
8. Controller acessa via SecurityUtils.getProfessorAutenticado()

ROTAS PÚBLICAS (sem autenticação)
────────────────────────────────────────────────────────────────────────────
  POST /api/v1/auth/login
  POST /api/v1/auth/register
  GET /actuator/health/**
  GET /h2-console/** (apenas dev)
  GET /swagger-ui/** 
  GET /v3/api-docs/**

ROTAS PROTEGIDAS (requer JWT válido)
────────────────────────────────────────────────────────────────────────────
  Todas as outras (CRUD de turmas, alunos, redações, etc)

CONTROLE DE ACESSO
────────────────────────────────────────────────────────────────────────────
Professor só acessa seus próprios dados:
  • Turmas: verificação findByIdAndProfessorId
  • Alunos: verificação findByIdAndTurmaProfessorId
  • Redações: verificação findByIdAndProfessorId
  • etc

Se tentar acessar recurso de outro professor: 404 (ResourceNotFoundException)

CRIPTOGRAFIA
────────────────────────────────────────────────────────────────────────────
  • Senhas: BCrypt (salt gerado automaticamente)
  • JWT Secret: HMAC com chave segura (deve estar em variável de ambiente)

12. TRATAMENTO DE ERROS
================================================================================

GlobalExceptionHandler trata 6 tipos de exceção:

1. ResourceNotFoundException (404)
   Code: RESOURCE_NOT_FOUND
   Exemplo: Turma/Redação não encontrada
   
2. BusinessException (400)
   Code: BUSINESS_RULE_VIOLATION
   Exemplo: Soma de critérios != 100%
   
3. UnauthorizedException (401)
   Code: UNAUTHORIZED
   Exemplo: Credenciais inválidas
   
4. ExternalServiceException (502)
   Code: EXTERNAL_SERVICE_ERROR
   Exemplo: Erro ao chamar OpenAI
   
5. MethodArgumentNotValidException (400)
   Code: VALIDATION_ERROR
   Exemplo: Campo obrigatório não preenchido
   Retorna lista de erros por campo
   
6. Exception (500)
   Code: INTERNAL_ERROR
   Exemplo: Erro inesperado

Formato de resposta:
{
  "status": 400,

  "message": "Erro na validação dos dados",

STATUS: ✅ COMPLETO

FEATURES IMPLEMENTADAS: 6 camadas de segurança

1. RATE LIMITING (Bucket4j)
   ─────────────────────────────────────────────────────────────────
   Arquivo: RateLimitConfig.java
   - Limita 100 requisições por minuto (10 segundos)
   - Limita 5 requisições por minuto para /auth/* (endpoints críticos)
   - Suporta X-Forwarded-For para proxies
   - Bucket4j v7.6.0 (thread-safe, em memória)

   Arquivo: RateLimitFilter.java (Servlet Filter)
   - Intercepta todas as requisições antes do controller
   - Valida contra bucket do IP
   - Retorna HTTP 429 Too Many Requests se excedido
   - Headers: X-Rate-Limit-Remaining, X-Rate-Limit-Retry-After-Seconds

   Uso: Automático, sem necessidade de configuração adicional

3. OPTIMISTIC LOCKING HANDLING
   ─────────────────────────────────────────────────────────────────
   Arquivo: GlobalExceptionHandlerHardened.java
   
   Novo handler:
   @ExceptionHandler(ObjectOptimisticLockingFailureException.class)
   - Detecta modificação concorrente de mesmo recurso
   - Retorna HTTP 409 Conflict
   - Code: OPTIMISTIC_LOCK_ERROR
   - Mensagem: "Recurso foi modificado por outro usuário..."

   Cenário:
   1. Usuário A abre turma (version=1)
   2. Usuário B abre turma (version=1)
   3. Usuário B salva turma (version→2)
   4. Usuário A tenta salvar (version ainda=1) → 409 Conflict
   5. Usuário A recarrega e tenta novamente

   Implementação: @Version Integer em todas as entidades
